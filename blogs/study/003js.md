## 2.1从输入 URL 到页面加载完成，发生了什么？

整个过程可以拆解为以下核心阶段：

#### 一、用户输入与导航启动

###### 判断输入类型

浏览器 UI 线程首先分析输入是**网址**还是**搜索关键词**。若是网址，自动补全协议（如 `https://`）；若是关键词，则调用默认搜索引擎拼接成搜索URL。

###### 安全检查与重定向

- 检查本地 **HSTS 预加载列表**，如果该域名强制 HTTPS，则内部将 `http://` 直接改写为 `https://`。
- 触发当前页面的 `beforeunload` 事件（可能弹出离开确认）。

###### Service Worker 拦截

如果该域已注册 Service Worker，则导航请求会被它拦截，可从本地 CacheStorage 提供离线内容，或代理请求。

###### 准备网络请求

浏览器主进程把“发起导航”任务交给网络线程（或网络进程），开始正式的资源获取。

#### 二、DNS 解析（域名 → IP 地址）

网络线程依次查询 DNS 缓存，顺序为：

1. 浏览器 DNS 缓存
2. 操作系统 hosts 文件
3. 本地路由器缓存
4. ISP（互联网服务提供商）的 DNS 服务器

若均未命中，ISP 的 DNS 服务器会发起**递归查询**：从根域名服务器 → 顶级域（.com/.org 等）服务器 → 权威 DNS 服务器，最终得到 IP 地址。  
现代浏览器会使用 **Happy Eyeballs** 算法同时尝试 IPv4 和 IPv6，并选用响应最快的。如果站点使用了 CDN，此时返回的 IP 将是离用户最近的边缘节点地址。

#### 三、建立网络连接

根据协议不同，连接建立过程有所区别：

###### 1. 经典 TCP + TLS（HTTP/1.1 或 HTTP/2）

- **TCP 三次握手**：`SYN` → `SYN-ACK` → `ACK`，在 TCP 层面建立全双工通道。
- **TLS 握手**（以 TLS 1.3 为例，更精简）：
  - 客户端发送 `ClientHello`（支持加密套件、密钥分享参数、SNI 等）。
  - 服务器回复 `ServerHello`，并附上**证书链**，随后用协商的密钥生成材料完成加密通道建立（1-RTT，若为 0-RTT 恢复会话更快）。
  - 浏览器验证证书：是否由受信 CA 签发、证书域名是否匹配、是否过期、吊销状态（OCSP 装订/CRL）等。
  - 对称会话密钥生成，后续应用数据都经过加密传输。

###### 2. QUIC（HTTP/3）

QUIC 基于 UDP，**将传输层加密和握手合并**。首次连接仅需 1-RTT 完成加密与流控建立，复用时甚至可实现 0-RTT，且无 TCP 队头阻塞问题，连接迁移更平滑。现代浏览器对支持 QUIC 的服务器会优先尝试。

---

#### 四、发送 HTTP 请求

连接建立后，浏览器构造 HTTP 请求报文：

- **请求行**：方法（GET/POST 等）、路径、协议版本。
- **请求头**：`Host`、`User-Agent`、`Accept`、`Cookie`、缓存协商字段（`If-None-Match` / `If-Modified-Since`）、安全头等。
- 若为 HTTP/2，会使用 **HPACK 头部压缩** 及**多路复用**在同一 TCP 连接上并发传输多个请求流；HTTP/3 则用 QPACK 压缩。

此时会先检查**浏览器 HTTP 缓存**：

- 强缓存命中（`Cache-Control: max-age` 未过期或 `Expires`） → 直接使用本地缓存，不发请求。
- 协商缓存 → 带 `ETag` 或 `Last-Modified` 条件发起请求，服务器返回 304 则用缓存。

#### 五、服务器处理请求

服务器端可能经历多层转发：

- **反向代理 / 负载均衡**（Nginx、HAProxy 等）接收请求，转发给具体应用服务器。
- 应用层处理业务逻辑，可能查询数据库、访问 Redis 缓存、调用内部微服务等。
- 若为**服务端渲染**（SSR），服务器会执行 JavaScript 生成完整 HTML 字符串。
- 最终组装 HTTP 响应：状态码（200、301、302、304、404、500 等）、响应头（`Content-Type`、`Cache-Control`、`Set-Cookie`、CORS 头、CSP 策略等）和响应体（HTML、JSON 等）。

---

#### 六、浏览器接收并处理响应

网络线程收到响应头后，立即解析：

###### 状态码处理

- `3xx` 重定向 → 根据 `Location` 发起新请求，并检查重定向次数防止死循环。
- `2xx` → 按 `Content-Type` 处理，`text/html` 则进入 HTML 渲染流程。
- `304` → 使用本地缓存资源。

###### 安全策略校验

- 检查 `Content-Security-Policy` 头，限制后续资源加载或脚本执行。
- 若 HTTPS 页面中混入 HTTP 资源（混合内容），浏览器可能拦截或降级处理。
- 应用 CORB/COOP/COEP 等跨域隔离策略。

###### 提交导航

当所有安全检查通过，网络进程把数据流交给渲染进程，浏览器 UI 开始更新地址栏、安全锁图标，并恢复访问历史。

---

#### 七、前端页面渲染（关键渲染路径）

渲染进程拿到 HTML 字节流后，展开密集工作：

###### 1. 构建 DOM 树

HTML 解析器（主线程）逐字节解码，通过**词法分析**生成 Token，再由语法分析构建 DOM 树。  
**预加载扫描器**（Preload Scanner）同时运行，提前发现 `<img>`、`<link>`、`<script>` 等外部资源，发出网络请求，减少等待。

###### 2. 加载与解析 CSS

遇到外部样式表 `<link>`，会发起请求并解析为 **CSSOM 树**（CSS 对象模型）。  
**CSS 不阻塞 DOM 解析，但阻塞渲染**，因为渲染树需联合 CSSOM。它也会**阻塞后续 JavaScript 执行**（JS 可能查询样式）。

###### 3. JavaScript 处理

- **同步脚本**（无 `async`/`defer`）：暂停 HTML 解析，等待脚本下载并执行完毕，因为脚本可能修改 DOM。
- **`defer` 脚本**：异步下载，在 DOM 解析完成后、`DOMContentLoaded` 事件前按顺序执行。
- **`async` 脚本**：异步下载，下载完立即执行，执行时可能中断 HTML 解析，执行顺序无关。

###### 4. 构建渲染树（Render Tree）

将 DOM 树与 CSSOM 树结合，生成只包含**可见节点**的渲染树（`display:none` 的元素不在其中，`visibility:hidden` 元素仍占位）。并计算出每个节点的**最终计算样式**（Computed Style）。

###### 5. 布局（Layout / Reflow）

从根节点开始遍历渲染树，计算每个元素的**几何信息**（坐标、宽高、盒模型边界等），生成布局树。可能因流式布局多次迭代。

###### 6. 分层与绘制（Paint）

浏览器对特定元素（如 3D 变换、`<video>`、`<canvas>`、`overflow:scroll` 等）创建独立的**合成层**，形成图层树（Layer Tree）。  
主线程为每个图层生成**绘制指令列表**（描述先画背景、再画边框等的顺序）。

###### 7. 合成与显示（Compositing）

- 绘制指令列表交给**合成线程**，它将每一图层切分成小块（Tile），交给 **GPU 进程** 进行栅格化（Rasterization，将矢量指令转为像素位图）。
- 所有图块完成栅格化后，合成线程通过 GPU 将它们拼接合成最终的屏幕图像，最后通过 IPC 交给浏览器主进程显示。

> **重要特性**：合成在合成线程完成，不占用主线程。这意味着即使主线程被 JS 阻塞，页面的滚动、CSS 动画依旧能流畅运行。


#### 八、页面生命周期与完成

- **`DOMContentLoaded` 事件**：DOM 构建完毕，所有 `defer` 脚本执行完，此时用户可看到部分内容，但图片等资源可能仍在加载。
- **`load` 事件**：页面及其所有子资源（图片、样式表、脚本、框架等）全部加载完毕。
- 之后浏览器进入可交互状态，并持续处理异步任务、更新 `requestAnimationFrame`、响应用户事件，形成完整的动态网页体验。


#### 九、贯穿全程的性能与安全优化

- **资源提示**：`<link rel="dns-prefetch">`、`preconnect`、`preload`、`prefetch` 在不同阶段提前做 DNS 解析、连接建立或资源缓存，大幅缩短后续请求的延迟。
- **缓存层次**：Service Worker Cache、HTTP 缓存、浏览器的内存缓存与磁盘缓存，让命中缓存的请求几乎零延迟。
- **安全防线**：混合内容拦截、CSP 策略、HTTP Strict-Transport-Security、CORS 校验等，在 URL 输入到渲染的每个环节都可能发挥作用。


整个流程涉及浏览器多个进程（主控、网络、渲染、GPU、插件等）的精妙协作，瞬间完成从“一串字符”到“完整页面”的转化。

## 2.2 无感刷新 Token（Access Token 自动续期）完整方案

当 Access Token 过期后，前端自动使用 Refresh Token 获取新的 Access Token，然后重新发送失败的请求，整个过程用户无感知，无需重新登录。

典型流程：

```text
用户登录
    ↓
获得 AccessToken（15分钟）
获得 RefreshToken（7~30天）
    ↓
正常访问接口
    ↓
AccessToken 过期
    ↓
接口返回 401
    ↓
调用 /auth/refresh
    ↓
获得新的 AccessToken
    ↓
重试原请求
    ↓
用户无感知
```


#### Access Token

特点：

- 生命周期短（15分钟~1小时）
- 每次请求都携带
- 用于接口鉴权
- 泄露风险相对较低

示例：

```http
Authorization: Bearer eyJhbGciOi...
```

#### Refresh Token

特点：

- 生命周期长（7天~30天）
- 专门用于刷新 Access Token
- 不参与业务接口鉴权
- 安全要求更高

#### Token 存储方案

##### Access Token

推荐：

```text
内存
Redux
Pinia
Zustand
sessionStorage
```

不推荐：

```text
localStorage
```

原因：

```text
容易被 XSS 窃取
```

最佳实践：

特点：

- JS 无法读取
- 浏览器自动携带
- 防止 XSS 窃取
- 安全性最高



#### Refresh 接口如何知道当前用户是谁？


```ts
axios.post('/auth/refresh')
```

什么参数都没传。后端怎么知道是谁？

答案：

```text
通过 Refresh Token 识别用户
```

##### 方案一：Refresh Token 本身是 JWT

Refresh Token 内容：

```json
{
  "userId": 1001,
  "exp": 1788888888
}
```

刷新时：

```ts
const refreshToken =
  req.cookies.refreshToken

const payload = jwt.verify(
  refreshToken,
  REFRESH_SECRET
)

const userId = payload.userId
```

优点：

```text
无需查数据库
性能高
```

缺点：

```text
难以主动失效
无法踢用户下线
```



##### 方案二：Refresh Token 是随机字符串（推荐）

登录：

```text
RefreshToken:
f8a2c9b7-xxxx-xxxx
```

数据库：

| refresh_token | user_id | expire_at |
|--------------|----------|------------|
| f8a2c9b7 | 1001 | 2026-07-01 |

刷新：

```ts
const refreshToken =
  req.cookies.refreshToken

const session =
  await db.findToken(refreshToken)

const userId = session.userId
```

优点：

```text
可主动失效
支持踢人下线
支持单设备登录
支持多端管理
安全性更高
```

目前主流互联网公司基本采用这种方案。

#### 无感刷新核心实现

##### 全局状态

```ts
let isRefreshing = false

let pendingRequests = []
```

作用：

```text
isRefreshing
避免多个刷新请求同时发起

pendingRequests
缓存等待重试的请求
```

##### 刷新 Token 方法

```ts
async function refreshToken() {
  try {
    const response =
      await axios.post('/auth/refresh')

    const newToken =
      response.data.accessToken

    setAccessToken(newToken)

    return newToken
  } catch (error) {
    clearUserSession()

    return null
  }
}
```


##### Axios 响应拦截器

```ts
axios.interceptors.response.use(
  response => response,

  async error => {
    const originalRequest =
      error.config

    if (
      error.response?.status !== 401 ||
      originalRequest._retry
    ) {
      return Promise.reject(error)
    }

    originalRequest._retry = true

    if (isRefreshing) {
      return new Promise(
        (resolve, reject) => {
          pendingRequests.push({
            resolve,
            reject,
            request: originalRequest
          })
        }
      )
    }

    isRefreshing = true

    try {
      const newToken =
        await refreshToken()

      if (!newToken) {
        throw error
      }

      originalRequest.headers.Authorization =
        `Bearer ${newToken}`

      pendingRequests.forEach(item => {
        item.request.headers.Authorization =
          `Bearer ${newToken}`

        item.resolve(
          axios(item.request)
        )
      })

      pendingRequests = []

      return axios(originalRequest)
    } catch (refreshError) {
      pendingRequests.forEach(item => {
        item.reject(refreshError)
      })

      pendingRequests = []

      clearUserSession()

      return Promise.reject(refreshError)
    } finally {
      isRefreshing = false
    }
  }
)
```


#### 为什么需要并发锁？

假设：

```text
AccessToken 已过期
```

同时发出：

```text
请求A
请求B
请求C
请求D
请求E
```

全部返回：

```text
401
```

如果没有锁：

```text
refresh × 5
```

会导致：

```text
大量无意义刷新
Token 覆盖
服务器压力增加
```


正确流程：

```text
请求A -> refresh
请求B -> 等待
请求C -> 等待
请求D -> 等待
请求E -> 等待
```

刷新成功：

```text
全部重试
```

只产生一次刷新请求。



#### Access Token 预刷新（优化）

除了等 401。还可以提前刷新。

JWT：

```json
{
  "exp": 1788888888
}
```

判断是否即将过期：

```ts
function isTokenExpiring(
  token,
  threshold = 60
) {
  const payload = JSON.parse(
    atob(token.split('.')[1])
  )

  return (
    payload.exp * 1000 -
      Date.now() <
    threshold * 1000
  )
}
```

请求前：

```ts
axios.interceptors.request.use(
  async config => {
    const token =
      getAccessToken()

    if (
      token &&
      isTokenExpiring(token)
    ) {
      const newToken =
        await refreshToken()

      config.headers.Authorization =
        `Bearer ${newToken}`
    }

    return config
  }
)
```

效果：

```text
减少 401
减少一次失败重试
提升体验
```


#### Refresh Token Rotation（推荐）

普通方案：

```text
AT1
RT1
```

刷新：

```text
AT2
RT1
```

RefreshToken 永远不变。

存在风险：

```text
RT1 被盗
攻击者可长期刷新
```


更安全方案：

第一次登录：

```text
AT1
RT1
```

刷新：

```text
AT2
RT2
```

同时：

```text
RT1 失效
```

数据库：

```text
RT1 -> revoked
RT2 -> active
```

即使：

```text
RT1 被盗
```

也无法再次使用。

这种方案叫：

```text
Refresh Token Rotation
```

Google、Microsoft、Auth0 等主流认证系统都在使用。


#### Refresh Token 失效怎么办？

刷新接口返回：

```http
401 Unauthorized
```

说明：

```text
RefreshToken 已过期
RefreshToken 被撤销
RefreshToken 非法
```

此时：

```ts
clearUserSession()

router.push('/login')
```

用户重新登录。


#### 其他

1. 某些接口（如登录、注册、刷新接口本身）不应该进入刷新流程，否则会造成死循环。建议补充：

```js
const whiteList = ['/auth/login', '/auth/refresh'];
if (whiteList.some(url => originalRequest.url.includes(url))) {
  return Promise.reject(error);
}
```

2. 默认情况下 Cookie 会自动附加到任何同源请求（包括恶意网站诱导用户发出的跨站请求）
```js
res.cookie(
  'refreshToken',
  refreshToken,
  {
    httpOnly: true,
    secure: true,
    sameSite: 'strict',
    path: '/auth/refresh',
    maxAge: 30 * 24 * 60 * 60 * 1000
  }
)
```

假设用户登录了： `https://app.company.com`

浏览器里有：

```
Cookie:
refreshToken=xxx
```
此时用户访问：`https://evil.com`

恶意网站偷偷执行：

```html
<form
 action="https://app.company.com/auth/refresh"
 method="POST">
</form>

<script>
document.forms[0].submit()
</script>
```

攻击者的目的：利用浏览器自动带 Cookie调用 refresh 接口，这就是 CSRF。

没有 SameSite

如果：

```
Set-Cookie:
refreshToken=xxx
```
浏览器会认为：这是合法 Cookie,于是：

```
evil.com
   ↓
POST /auth/refresh
   ↓
Cookie 自动携带
```
攻击成功。

```
SameSite=Strict
```
如果：
```
Set-Cookie:
refreshToken=xxx;
SameSite=Strict
```
浏览器发现：

请求来源：
```
evil.com
```

目标：
```
app.company.com
```
属于：Cross-Site Request.于是不发送 Cookie

实际请求变成：
```
POST /auth/refresh
Cookie: （空）
```

后端：
```
req.cookies.refreshToken
```
得到： undefined,刷新失败,攻击失败。
