## 2.2 无感刷新 Token（Access Token 自动续期）完整方案

当 Access Token 过期后，前端自动使用 Refresh Token 获取新的 Access Token，然后重新发送失败的请求，整个过程用户无感知，无需重新登录。

典型流程：

```text
用户登录
    ↓
获得 AccessToken（15分钟）
获得 RefreshToken（7~30天）
    ↓
正常访问接口
    ↓
AccessToken 过期
    ↓
接口返回 401
    ↓
调用 /auth/refresh
    ↓
获得新的 AccessToken
    ↓
重试原请求
    ↓
用户无感知
```


#### Access Token

特点：

- 生命周期短（15分钟~1小时）
- 每次请求都携带
- 用于接口鉴权
- 泄露风险相对较低

示例：

```http
Authorization: Bearer eyJhbGciOi...
```

#### Refresh Token

特点：

- 生命周期长（7天~30天）
- 专门用于刷新 Access Token
- 不参与业务接口鉴权
- 安全要求更高

#### Token 存储方案

##### Access Token

推荐：

```text
内存
Redux
Pinia
Zustand
sessionStorage
```

不推荐：

```text
localStorage
```

原因：

```text
容易被 XSS 窃取
```


##### Refresh Token

最佳实践：

```http
Set-Cookie:
refreshToken=xxxx;
HttpOnly;
Secure;
SameSite=Strict;
```

特点：

- JS 无法读取
- 浏览器自动携带
- 防止 XSS 窃取
- 安全性最高



#### Refresh 接口如何知道当前用户是谁？


```ts
axios.post('/auth/refresh')
```

什么参数都没传。后端怎么知道是谁？

答案：

```text
通过 Refresh Token 识别用户
```

##### 方案一：Refresh Token 本身是 JWT

Refresh Token 内容：

```json
{
  "userId": 1001,
  "exp": 1788888888
}
```

刷新时：

```ts
const refreshToken =
  req.cookies.refreshToken

const payload = jwt.verify(
  refreshToken,
  REFRESH_SECRET
)

const userId = payload.userId
```

优点：

```text
无需查数据库
性能高
```

缺点：

```text
难以主动失效
无法踢用户下线
```



##### 方案二：Refresh Token 是随机字符串（推荐）

登录：

```text
RefreshToken:
f8a2c9b7-xxxx-xxxx
```

数据库：

| refresh_token | user_id | expire_at |
|--------------|----------|------------|
| f8a2c9b7 | 1001 | 2026-07-01 |

刷新：

```ts
const refreshToken =
  req.cookies.refreshToken

const session =
  await db.findToken(refreshToken)

const userId = session.userId
```

优点：

```text
可主动失效
支持踢人下线
支持单设备登录
支持多端管理
安全性更高
```

目前主流互联网公司基本采用这种方案。

#### Refresh Token 如何传给后端？

##### 方式一：HttpOnly Cookie（推荐）

登录成功：

```http
Set-Cookie:
refreshToken=xxxx;
HttpOnly;
Secure;
```

前端：

```ts
axios.post('/auth/refresh')
```

实际请求：

```http
POST /auth/refresh

Cookie:
refreshToken=xxxx
```

浏览器自动携带。



##### 方式二：请求体携带

```ts
axios.post('/auth/refresh', {
  refreshToken
})
```

缺点：

```text
RefreshToken 暴露给 JS
容易被 XSS 获取
```
一般不推荐。


#### 无感刷新核心实现

##### 全局状态

```ts
let isRefreshing = false

let pendingRequests = []
```

作用：

```text
isRefreshing
避免多个刷新请求同时发起

pendingRequests
缓存等待重试的请求
```

##### 刷新 Token 方法

```ts
async function refreshToken() {
  try {
    const response =
      await axios.post('/auth/refresh')

    const newToken =
      response.data.accessToken

    setAccessToken(newToken)

    return newToken
  } catch (error) {
    clearUserSession()

    return null
  }
}
```


##### Axios 响应拦截器

```ts
axios.interceptors.response.use(
  response => response,

  async error => {
    const originalRequest =
      error.config

    if (
      error.response?.status !== 401 ||
      originalRequest._retry
    ) {
      return Promise.reject(error)
    }

    originalRequest._retry = true

    if (isRefreshing) {
      return new Promise(
        (resolve, reject) => {
          pendingRequests.push({
            resolve,
            reject,
            request: originalRequest
          })
        }
      )
    }

    isRefreshing = true

    try {
      const newToken =
        await refreshToken()

      if (!newToken) {
        throw error
      }

      originalRequest.headers.Authorization =
        `Bearer ${newToken}`

      pendingRequests.forEach(item => {
        item.request.headers.Authorization =
          `Bearer ${newToken}`

        item.resolve(
          axios(item.request)
        )
      })

      pendingRequests = []

      return axios(originalRequest)
    } catch (refreshError) {
      pendingRequests.forEach(item => {
        item.reject(refreshError)
      })

      pendingRequests = []

      clearUserSession()

      return Promise.reject(refreshError)
    } finally {
      isRefreshing = false
    }
  }
)
```


#### 为什么需要并发锁？

假设：

```text
AccessToken 已过期
```

同时发出：

```text
请求A
请求B
请求C
请求D
请求E
```

全部返回：

```text
401
```

如果没有锁：

```text
refresh × 5
```

会导致：

```text
大量无意义刷新
Token 覆盖
服务器压力增加
```


正确流程：

```text
请求A -> refresh
请求B -> 等待
请求C -> 等待
请求D -> 等待
请求E -> 等待
```

刷新成功：

```text
全部重试
```

只产生一次刷新请求。



#### Access Token 预刷新（优化）

除了等 401。还可以提前刷新。

JWT：

```json
{
  "exp": 1788888888
}
```

判断是否即将过期：

```ts
function isTokenExpiring(
  token,
  threshold = 60
) {
  const payload = JSON.parse(
    atob(token.split('.')[1])
  )

  return (
    payload.exp * 1000 -
      Date.now() <
    threshold * 1000
  )
}
```

请求前：

```ts
axios.interceptors.request.use(
  async config => {
    const token =
      getAccessToken()

    if (
      token &&
      isTokenExpiring(token)
    ) {
      const newToken =
        await refreshToken()

      config.headers.Authorization =
        `Bearer ${newToken}`
    }

    return config
  }
)
```

效果：

```text
减少 401
减少一次失败重试
提升体验
```


#### Refresh Token Rotation（推荐）

普通方案：

```text
AT1
RT1
```

刷新：

```text
AT2
RT1
```

RefreshToken 永远不变。

存在风险：

```text
RT1 被盗
攻击者可长期刷新
```


更安全方案：

第一次登录：

```text
AT1
RT1
```

刷新：

```text
AT2
RT2
```

同时：

```text
RT1 失效
```

数据库：

```text
RT1 -> revoked
RT2 -> active
```

即使：

```text
RT1 被盗
```

也无法再次使用。

这种方案叫：

```text
Refresh Token Rotation
```

Google、Microsoft、Auth0 等主流认证系统都在使用。


#### Refresh Token 失效怎么办？

刷新接口返回：

```http
401 Unauthorized
```

说明：

```text
RefreshToken 已过期
RefreshToken 被撤销
RefreshToken 非法
```

此时：

```ts
clearUserSession()

router.push('/login')
```

用户重新登录。


#### 其他

1. 某些接口（如登录、注册、刷新接口本身）不应该进入刷新流程，否则会造成死循环。建议补充：

```js
const whiteList = ['/auth/login', '/auth/refresh'];
if (whiteList.some(url => originalRequest.url.includes(url))) {
  return Promise.reject(error);
}
```

2. 默认情况下 Cookie 会自动附加到任何同源请求（包括恶意网站诱导用户发出的跨站请求）
```js
res.cookie(
  'refreshToken',
  refreshToken,
  {
    httpOnly: true,
    secure: true,
    sameSite: 'strict',
    path: '/auth/refresh',
    maxAge: 30 * 24 * 60 * 60 * 1000
  }
)
```

假设用户登录了： `https://app.company.com`

浏览器里有：

```
Cookie:
refreshToken=xxx
```
此时用户访问：`https://evil.com`

恶意网站偷偷执行：

```html
<form
 action="https://app.company.com/auth/refresh"
 method="POST">
</form>

<script>
document.forms[0].submit()
</script>
```

攻击者的目的：利用浏览器自动带 Cookie调用 refresh 接口，这就是 CSRF。

没有 SameSite

如果：

```
Set-Cookie:
refreshToken=xxx
```
浏览器会认为：这是合法 Cookie,于是：

```
evil.com
   ↓
POST /auth/refresh
   ↓
Cookie 自动携带
```
攻击成功。

```
SameSite=Strict
```
如果：
```
Set-Cookie:
refreshToken=xxx;
SameSite=Strict
```
浏览器发现：

请求来源：
```
evil.com
```

目标：
```
app.company.com
```
属于：Cross-Site Request.于是不发送 Cookie

实际请求变成：
```
POST /auth/refresh
Cookie: （空）
```

后端：
```
req.cookies.refreshToken
```
得到： undefined,刷新失败,攻击失败。
